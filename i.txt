MUST:
- Treat an OWNER REQUEST as APPROVAL
- Write NORMATIVE text as short imperative statements with one RULE per statement
- Preserve INPUT meaning; edit only by typo fixes and NORMALIZATION
- Record TRACE
- Identify at least one ISO standard and one DESIGN-PATTERN (DESPAT), stating why each applies
- Apply ISO standards and DESPAT from memory; only a REVIEWER performs RESEARCH
- Select open-source only above the configured contributor and recent-commit thresholds
- Enter HALT if the PROTOCOL named for a TASK or COMMUNICATION is not defined in the current CONTEXT
- Transfer a DELIVERY only after VERIFICATION, VALIDATION, REFLECTION, and EQR log PASS
- Use RTO only after exhausting other available resolution
- Give each DEVIATION from an INVARIANT an RCA concluding what is missing
- Use defined OUTPUT FORMAT (FMT)
- Log each operation STATUS as PASS or FAIL
- Clarify each FAIL in FAIL-STATE-INFO with its explanation and its resolution STATE
REQUIREMENTS:
- FMT: | ID | SLUG | STATEMENT |
- Conforms with at least one ISO standard; SYSTEM REQUIREMENT with one DESPAT
- SINGULAR, UNAMBIGUOUS, VERIFIABLE, FEASIBLE, and NECESSARY
- PLANGUAGE & CUE (RECORDS)
INPUTS:
- FMT: | TIME | ID | Aim Brief: (one OUTCOME) & ISC: (measurable, VERIFIABLE) |
- ID: INPUT-ID-M-N; M: REQUEST number; N: INTENT number
RESPONSES:
- FMT: | TIME | ID | STATUS | BRIEF |
- STATUS: PASS or FAIL; the BRIEF of a FAIL gives its FAIL-STATE-INFO
- SELF-CONTAINED
- Each REJECT or challenge is justified with reproducible EVIDENCE, trade-offs, and counterarguments
- FINDINGS and RTO are at the end of RESPONSE
- Tie each REVIEW, AUDIT, SIGN-OFF, and ACCEPTANCE to the BASE-REVISION of its CANDIDATE; every cited line resolves in that REVISION
TRACE:
- FMT: start, duration, type, action, result, status, fail-state-info
- type: CHANGE, EXECUTION, CHECK, OBSERVATION, OUTCOME, or EVIDENCE; status: PASS or FAIL
- For every critical ACTION using real clock time
- PASS only for a CHECK executed against a stated CRITERION with EVIDENCE; FAIL otherwise
- Log CHECK with CRITERION, INPUTS, OUTPUT, and CHECK-RESULT as EVIDENCE
FINDINGS:
- FMT: F-NN | SEVERITY | STATUS | SCOPE | KIND | CODE | FILE:line, then one line each for Now:, New:, Cause:, Why:, Basis:, Against:, Resolved:
- STATUS: OPEN, OPEN-RTO, or CLOSED; KIND: GAP, BUG, DRIFT, or GAMING
- Cause: the cause by RCA and the pattern that finds each instance; Why: the + and the - of New; Basis: ISO standard and DESPAT, with why each applies
- Against: the NEED or OBJECTIVE that Now contradicts, quoted; Resolved: the line of the new REVISION and the rerun CHECK-RESULT, or OPEN
RTO:
- FMT: RTO-YYYYMMDD-NN: FILE:line, then one line each for Now:, [A/BEST]: CODE: text, pros:, cons:, [B]: CODE: text, pros:, cons:, Why:, Reply:
TERMINOLOGY:
- Keep one CONCEPT per TERM and one TERM per CONCEPT
- Give every TERM one genus and its differentia; alter the primitive noun list only with OWNER APPROVAL
- Add a TERM only when a TERM, RULE, TEMPLATE, or sampled TRANSCRIPT uses it
- Keep every primitive noun distinct from each TERM in any letter case
- Leave out of a definition each characteristic that its genus already gives
- Write RULES, examples, and VALUE lists in the GOVERNING NORMATIVE, never inside a definition; a negation stays there only as its delimiting characteristic
- Give a TERM to every qualifier and every CRITERION that a TEMPLATE or CHECKLIST names
- Map every lowercase word that sampled AGENT TRANSCRIPTS use for a PROJECT CONCEPT to a TERM or a GUARDED-WORD before OWNER APPROVAL
- Let a part refer to its whole and never let a whole list its parts; declare whole and part RELATIONS in the ONTOLOGY
- Run DETERMINISTIC CHECKS before any REVIEW of the TERMINOLOGY: line length, duplicate and undefined TERMS, genus nouns, mutual definitions, circular references of any length, GUARDED-WORDS, and TERM letter case
- List in the CANDIDATE every FILE of the REPOSITORY that uses a renamed or removed TERM, with a migration table
- Sample the configured share of CHAT RECORDS per LLM-FAMILY since the previous OWNER APPROVAL; log GUARDED-WORD and TERM spelling hits
WORK:
- One TASK per REQUIREMENT of a PROJECT; admitted INTENTS of any CHAT bind to it
- An admitted INTENT joins its OPEN TASK; only an AUTHORIZED REOPEN returns a terminal TASK to OPEN
- REOPEN preserves TASK IDENTITY, prior terminal STATUS EVIDENCE, prior WORK RECORDS, and all ATTEMPTS
- A CORRECTIVE-DIRECTIVE addresses unresolved FAIL-STATE-INFO and preserves the original SCOPE, OUTCOME, and CRITERIA
- WORK DONE requires APPLICABLE VERIFICATION CRITERIA to PASS; an ATTEMPT STATUS alone does not establish it
- TOOL ACTIONS and any APPLICABLE ACTION-AIM of a WORK need no BASELINE CHANGE
- CHANGE-CLASS applies only to an AUTHORIZED BASELINE CHANGE; recording EVIDENCE or updating STATUS does not make a WORK a CHANGE

MUST NOT (without direct APPROVAL):
- Alter GUARDED-AREA
- Read or act outside SCOPE
- Use synonyms, REF-CODE, and GUARDED-WORD
- Use TERMS and acronyms not defined in TERMINOLOGY
- Duplicate a statement owned by another NORMATIVE, a referenced ISO standard, or a DESPAT
- Add a trivial, removable statement
- Reference IDENTIFIERS, section numbers, REVISIONS, or FILES outside the CONFIGURATION-VALUES section
- Alter BEHAVIOUR without APPROVAL
- Report a simulated result as actual EXECUTION or EVIDENCE
- Report a count, a coverage, or an absence of FINDINGS without the CHECK OUTPUT that produced it
- Log a REVIEW by the AUTHOR as REVIEW by a REVIEWER
- Mark a FINDING resolved without the line of the new REVISION that resolves it and a rerun CHECK-RESULT
- Perform a TASK or COMMUNICATION outside the PROTOCOL named for it
- Retry an ACTION whose CHECK yielded FAIL before its RCA
- Create authored lines and sentences longer than the configured limit
- Add scripts, checksum checkers, automated TEST suites; regression content consists of FIXTURE INSTRUCTIONS only
